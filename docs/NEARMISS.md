# Near-miss decompilations (readable C, NOT byte-identical)

This registry lists **readable C not yet verified as byte-identical compiled code in the linked
game**. An object can score 100% while its local data still prevents correct linking.
Residual descriptions are working diagnoses, not proof that a source change
cannot fix them. Check prototypes, source spelling, and generated reference relocations before
calling a difference a compiler limitation; each has explained previously parked functions.
The C aims to preserve the original logic, but remains subject to review and correction.

## Why these exist

The decomp's primary goal is a maximally-faithful, byte-identical rebuild. For functions that are
genuinely wall-bound, an opaque `// INCLUDE_ASM` stub gives byte-identity but **zero readable source**
— useless as ground truth for the native-port effort. A `// NEARMISS` file instead commits the
readable, logically-faithful C **and** keeps the boot ELF byte-identical:

- The file's first line is `// NEARMISS <func> (...)`; `build.py` / `fill_unmatched.py` treat it like
  a stub — it is **not compiled, not an objdiff unit**, and **does not affect `matched_code`** (which
  continues to measure only true byte-match attempts).
- The linker fills the function's bytes from the **splat `.s`** (byte-identical), never from this C.
- Each file's header documents its **objdiff %** (best plain-C, reproducible via its `// COMPILER` /
  `// CFLAGS`) and the **precise divergence reason**.

To convert a near-miss to a true match later, reproduce the byte-exact bytes from C and drop the
`// NEARMISS` marker (it becomes a normal compiled unit at 100%).

**Companions of asm-bodied units (`src/readable/`, first-level lane 2026-10-01).** A function
whose `src/<f>.c` is a CodeWarrior `asm` body already links byte-identically and counts as a matched
unit. Turning it into a NEARMISS file would drop it from `matched_code` and remove an asm body the
user chose to keep, so its readable C lives in `src/readable/<f>.c` instead, with the same NEARMISS
header (objdiff %, compiler, divergence). `tools/decomp/build.py` and `tools/decomp/link.py` only
glob `src/*.c`, so these files are never compiled or linked; the asm file ends with a one-line
pointer to its companion. The registry rows below say "Companion C in src/readable/". To promote
one, reach 100% and replace the asm body in `src/<f>.c` with the C (then delete the companion).

**Unmarked C that is not byte-matched (FUNCTIONS.csv `c_asm_fallback` / `c_partial`, 2026-10-20).**
`tools/decomp/reconcile_functions_csv.py` found 52 boot functions whose `src/<f>.c` was ordinary C
without a `// NEARMISS` marker yet not objdiff 100%. 50 of them (`c_asm_fallback`) linked from the
original `.s` through fill_unmatched's explicit `SIZE_DRIFT_FORCE_ASM` / `GPREL_FORCE_ASM` lists,
and their bodies had never been checked against the original instructions. Decomp lane round 3
(2026-10-20) rewrote all 50 from the original instructions. Most of the old bodies were wrong, not
just unmatched: func_00110BC0 / func_00110C48 read the wrong fallback string, func_001098E0 called
func_001026A0 where the original tail-calls func_0010A400, func_00107CB8 dereferenced one level too
far, and func_001145A0 used a misnamed symbol for an offset. 45 are now byte-matched (21 SDK-range
units with ee-gcc, 24 game units with mwcc 2.3.3; their list entries are removed) and the other
5 became `// NEARMISS` files (func_001899C0, func_001D4A90, func_001D71A0, func_001E0C80,
func_001FC9B0; round 4 byte-matched func_001D4A90 and round 7 func_001899C0, the other three are in
the registry below).

expected object spells as a literal upper half (0x7000) plus offset 0x38A0 while the C names

compiled objects with the boot ELF byte-identical. This is the splat literal-vs-relocation case
recorded as tested and rejected in build.py (s86, 0x700038A0); objdiff 100 needs an
expected-object normalizer for it, not a source change.


**Measure against a fresh expected object (2026-10-20).** `tools/decomp/build.py build` rebuilds
`build/expected/<f>.o` only for compiled units, so a NEARMISS function's expected object can be older
than a symbol relabel. Rebuilding all 716 from the normalized `.s` (as `integrate_nearmiss.py` does)
changed 48 scores by up to 0.5 points, most of them SDK callers of the syscall stubs relabelled on
2026-09-27; rows not touched since keep the older figure. Decomp lane round 5 also corrected the
vram column of eight named functions (the integrator used to slice it out of the name).

**Scratchpad residuals: measure per address first (decomp lane round 6, 2026-10-20).** Ten rows
left the registry as byte-matches (func_00158D30, func_00175CF0, func_00176180, func_00177CF0,
func_00177F40, func_0019AB20, func_0019B2C0, func_0019B4C0, func_0019B8C0, func_0019BA80). Seven of
them blamed the compiler (an FP scheduling or coloring wall, a delay-slot fill no source change
fixes); the main fix was per-address scratchpad externs opted in with `// SPAD:`
(MATCHING_GUIDE idiom-32 and "Decomp lane round 6"). Before trusting a row whose diff touches a
`0x7000xxxx` access, run `tools/match/spad_sweep.py` on it.

**Same-TU callees: try `// TU_STATIC:` (decomp lane round 7, 2026-10-20).** Five rows left the
registry as byte-matches (func_001796C0, func_001899C0, func_001F6BB0, func_0021B9A0, func_0021D800). Their
headers blamed register colouring, CodeWarrior branch lowering or interprocedural analysis; the
original compiler knew the register use of a callee earlier in the same file. With that callee
compiled as a `static` function of the caller's file (`// TU_STATIC:`, tools/decomp/tu_static.py,
MATCHING_GUIDE "Decomp lane round 7") mwcc 2.3.3 reproduces it. func_001F6BB0's old body was also
wrong: it called func_001F6640 and func_001F66F0 without the pointer each one reads. When a row's
diff sits at a call to a nearby lower-address callee (a missing argument move, a value kept in an
argument register across the call, a branch-likely after it), check whether that callee is a
byte-matched unit and try it as a TU static.

**Reconcile declarations before trusting a TU-static measurement (decomp lane round 8, 2026-10-20).**
Five more rows left the registry as byte-matches (func_0012B410, func_001AA840, func_001BD560,
func_001D4B80, func_001D4C30), and anim_matrix_player, func_0016EBA0 and func_001BAD40 have
corrected bodies (MATCHING_GUIDE "Decomp lane round 8"). Three of the five had a wrong call: a
constant argument the target never sets (func_0012B410's 4, func_001BD560's 1) or the wrong
parameter slot (func_001AA840). A TU-static variant that fails to compile because the caller and
callee disagree on a call is a pointer to such a bug: read the target's argument registers at that
call before changing either declaration.

**Prototype fixes, a structural twin and the TU-static sweep (decomp2 lane round 1, 2026-10-20).**
func_00214020 and func_001E7570 left the registry as byte-matches and func_002044F0 has a corrected
body (MATCHING_GUIDE "Decomp2 lane round 1"). func_001E7570's "FP register wall" was its spelling:

for a callee whose own C disagrees with the call.

**Argument registers per call, then the exits (decomp2 lane round 3, 2026-10-21).** Eight rows
left the registry as byte-matches (func_001999C0, func_00197490, func_00198AF0, func_00198650,
func_00198D90, func_001D1AE0, func_001B6BF0, func_00183910) and func_00197D20 / func_00198F10 have
corrected or closer bodies (MATCHING_GUIDE "Decomp2 lane round 3"). Three bodies were wrong, not
just unmatched: func_001999C0 ran its D_00810CA5 hook for every arm, func_00197490 cleared +2 / +3
/ +8 in two cases that return at once, and func_00198AF0's state 2 test was inverted. Their old
headers called the residuals dead constants, delay slots and colouring. Compare each call's
argument registers with the target per class (`$a0..$t3`, `$f12..$f19`), and read where every
exit branch goes, before recording a wall.

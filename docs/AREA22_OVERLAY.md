# AREA22 overlay — decompilation status (lane A22C, 2026-09-28)

AREA22 is the area after AREA04 on the story route (game order AREA11 ->
AREA01 -> AREA00 -> AREA01 with the bridge lowered -> AREA02 -> AREA04 ->
AREA22; the port's docs/FIFTH_LEVEL_ROUTE.md records the change through
AREA04's door [37] into AREA22 entry 0, overlay id 0x13). Its code module
is `OVERLAY/AREA22.BIN`: overlay id 19, text 0xC0, data 0x800, bss
0x140C00, file 0x900 bytes. Like every overlay it is linked at 0x00823500
but runs 0x40 higher (the MWo3 header is loaded first), so link names are
the runtime address minus 0x40.

AREA22 is one of the two stub overlays (with AREA18; docs/OVERLAYS.md
section 2). Its text holds only the 0x40-byte entry pad and one 0x20-byte
function followed by zero padding to the end of text. Everything else in
the file is data. The area overview of the AREA22 arrival capture
(build/s88_a22, output of the area_overview tool over
route_a04/a04_05_progression_exit) finds the sub-0 nest group (0x823600),
deferred groups (0x8236B0) and placement records (0x823A20) in that data,
and every behaviour of the 54 live pool nodes there is a boot address, so
AREA22 gameplay is boot code driven by this data; there is no further
overlay code to decompile.

## Status

Both pieces are in `src/overlays/AREA22/` and both link from their compiled
objects (nothing is assembled from splat for the text). No split handling
was needed: there is no intra-overlay call, no fake split and no jump table
(`jt_pin.py` has nothing to pin).

| link name | runtime | size | status |
|---|---|---|---|
| func_overlay_AREA22_00823500 | 0x823540 | 0x4 (slot 0x40) | asm pad (entry nop, unchanged; user decision to keep asm bodies) |
| overlay_AREA22_func_00823540 | 0x823580 | 0x20 (slot 0x80) | C, byte-identical (default mwccmips, `-O4,p -sdatathreshold 4`; committed since 8fadca5) |

This lane changed only the header comment of
`overlay_AREA22_func_00823540.c` (the behaviour below); the code is
unchanged. `config/overlays/AREA22.lds` was regenerated by the link and is
identical to the committed file.

`overlay_match.py list AREA22` groups the two pieces into one function
named after the pad (size 0x60), because nothing but zero words precedes
0x823540 and the pad piece has no return. Two consequences, both tool-side
and outside this lane:

- `overlay_match.py check AREA22 .../overlay_AREA22_func_00823540.c` stops
  with a KeyError (the stem is not one of `list`'s names). The per-function
  check below uses a scratch copy of the AREA04 lane's section checker with
  the address-symbol pattern widened to the `overlay_AREA22_func_` form.
- The area overview (build/s88_a22, decomp b95f409) classifies the grouped
  function as AI ("nop sled, no code") and lists the init's C file as a
  stray source. The init is C and linked; only the pad is asm.

## Behaviour (from the byte-matched C and its caller)

`overlay_AREA22_func_00823540` stores four gp-relative boot words and
returns: D_00275C28 = 0x20, D_00275C1C = 0x00823E00, D_00275C2C = 0,
D_00275C24 = 0. The constant 0x00823E00 is the runtime address of the first
byte after the loaded file image (0x823500 + 0x900), where the zeroed
`.bss` begins; its link symbol is `D_overlay_AREA22_00823E00`. The boot
code indexes this word as a record base, D_00275C1C + i * 0xA060
(func_001E9580, func_001E9E60).

The caller is the boot function func_001E7780 (committed C). It first
zeroes D_00275C18, D_00275C1C, D_00275C20, D_00275C24, D_00275C28 and
D_00275C2C, builds key = (D_00810700 << 8) + D_00810701, and for key 0x1600
(area 22, sub 0) calls runtime 0x823580 with (0x1600, 0x1600). In the boot
symbol list that address is `area_dispatch_off0080_state0300` because keys
0x300/0x301 call the same address in AREA03's overlay; the name says
nothing about AREA22. The AREA22 init ignores both arguments. It leaves
D_00275C20 and D_00275C18 at zero, so func_001E7780's closing loop over
D_00275C2C records of D_00275C20 runs zero times. Compared with AREA04's
init (func_overlay_AREA04_00823AD0: D_00275C2C = 1 and a D_00275C20
pointer), AREA22 sets up no D_00275C20 record array.

## Binding

The native port needs no AREA22 overlay module for code: the only overlay
function sets four boot globals that the port's area setup must reproduce
(D_00275C1C = the bss start, D_00275C28 = 0x20, the rest zero), and the
area's behaviours are boot functions reached through the overlay's data
tables. The port already writes the same globals for other areas'
inits (`src/game/em_area02_overlay.c` for AREA02, `em_startup_load_gaps.c`
for AREA11) and reads the D_00275C1C record base in
`em_area01_exitb.c` (001E9580); it has no AREA22 counterpart yet. Nothing
in the port was edited by this lane.

## Known gaps

- The overlay's data section (0x800 bytes) is linked from splat's data
  assembly, as in every overlay; it is not expressed in C.
- `overlay_match.py` and the area overview misgroup the init with the pad
  (above); fixing that is a tools change outside this lane.
- The entry pad stays an asm body (user decision 2026-09-23).
